# 01 - Account Foundation: Tooling and Identity

Status: in progress

## Goal

Before writing any infrastructure code, set up a safe way for my machine
(and later, CI) to authenticate to AWS. Weak authentication in the
foundation would undermine everything built on top of it.

## Environment

| Item | Choice |

| Workstation | Windows 11 (PowerShell) |
| Secondary | Kali Linux VM (for scanning and testing later) |
| AWS account | Free tier |
| Primary region | eu-west-1 (Ireland) |
| IaC | Terraform |

## Steps completed

### 1. Installed the AWS CLI v2

```powershell
winget install -e --id Amazon.AWSCLI
aws --version
```

Result: `aws-cli/2.40.2` working.

Why: Terraform's AWS provider reads credentials from the same sources as
the AWS CLI, so a correctly configured CLI means a correctly configured
Terraform.

### 2. Root account protected with MFA

Root account sign-in uses a password plus a TOTP code from an authenticator app.

Why: the root user cannot be restricted by permission policies. If its
password leaks, the whole account (and bill) is compromised. MFA makes a
stolen password insufficient.

Follow-up improvements: register a second MFA device (backup), and consider
a passkey or hardware key, which is phishing-resistant.

### 3. Decision: how the CLI/Terraform authenticates

| | IAM user + access keys | IAM Identity Center | IAM user + `aws login` (chosen for now) |
|---|---|---|---|
| Credentials | Long-lived keys on disk | Short-lived, expire automatically | Short-lived (up to 12 h), refreshed by the CLI |
| Leak impact | Works until manually revoked | Expires within hours | Expires within hours |
| Cost / plan impact | Free | Needs an AWS Organization, which upgrades the account from the free plan to pay-as-you-go and expires free credits | Free, stays on free plan |

Identity Center was my first choice (it is the industry standard for human
access). When I started enabling it, the console warned that creating the
organization upgrades the account to a paid plan and expires free tier
credits immediately, and that the default multi-region setup adds KMS
charges. Since this is a learning project on a free account, I decided to
stay on the free plan.

Chosen approach: an IAM user with MFA, signing in from the CLI with
`aws login`, which uses browser sign-in to get temporary credentials
instead of storing permanent access keys. Identity Center remains a
planned future migration.

### 4. Decision: region eu-west-1

Identity Center is tied to one region and is hard to move later. eu-west-1
is mature, has the services this project needs, and fits the EU data
protection / EU AI Act theme. af-south-1 (Cape Town) is closer
geographically but is opt-in and has fewer services.

### 5. Created an IAM user and group

- User: `admin-solomon`, console access, autogenerated password with forced reset on first sign-in
- Group: `admins`, with `AdministratorAccess` and `SignInLocalDevelopmentAccess` attached
- Permissions are attached to the group, not the user (easier to manage, standard practice)
- `AdministratorAccess` is temporary scaffolding; it will be replaced by narrower roles (see Next)

### 6. MFA on the IAM user

Authenticator-app MFA enabled on `admin-solomon`, separate from the root account's MFA.

### 7. CLI authentication with `aws login`

```powershell
aws login
aws sts get-caller-identity
```

Output confirmed the CLI is acting as the IAM user, not root:

```
"Arn": "arn:aws:iam::<account-id>:user/admin-solomon"
```

(Account ID redacted in this repo.) Credentials are temporary and refreshed
by the CLI for up to 12 hours; no access keys are stored on disk. I declined
the optional prompt to configure AI coding agents with AWS access.

### 8. Cost guardrails and account inventory

- Root enabled "IAM user and role access to Billing information" (only root can), then switched back to the IAM user.
- Investigated a small month-to-date charge. The Bills page showed a net total of USD 0.00 because free plan credits offset it, with a few cents of gross cost under Key Management Service in us-east-1. No customer managed KMS keys or Secrets Manager secrets existed at the time of checking.
- Found a stopped `t3.micro` EC2 instance left over from an old tutorial in us-east-1 and terminated it. A stopped instance does not pay for compute, but its EBS volume is still billed, and a forgotten machine is an unmonitored asset.
- Created a **zero spend budget** (`zero-spend-alert`) that emails when spend goes above about one cent. Chosen because on a free plan any spend is a signal worth knowing about immediately.

Lesson: inventory what you own before building. Unknown assets are a
common audit finding, and knowing your assets is the first step of any
GRC program.

### Concept: ARN (Amazon Resource Name)

Format: `arn:partition:service:region:account-id:resource`. Every AWS
resource has one. IAM policies use ARNs to scope permissions precisely;
`"Resource": "*"` is a common least-privilege finding.

## some questions and answers

- Why not use the root user day to day? It is unrestricted and cannot be limited by policy; protect it with MFA and keep it for rare account-level tasks.
- Why short-lived credentials (`aws login`) instead of IAM access keys? They expire on their own, which removes the "leaked key" risk class. Identity Center is the industry-standard version of this; I chose the IAM user route because Identity Center requires an AWS Organization, which would have ended my free plan.
- What is least privilege? Granting only the permissions an identity needs. We apply it when designing permission sets.
- What is TOTP, and why is a passkey stronger? TOTP codes can be phished in real time on a fake login page; passkeys are bound to the real site.
